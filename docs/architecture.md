# Architecture

`llmah.py` builds `Assistant` and the terminal. `core.parser.Parser` produces a `Plan` containing typed `Operation` objects (`core.contracts`). `Validator` checks capability names, argument schemas, protected paths, and dependency DAGs before `Executor` invokes a registered callable. Results carry status, timing, error category, output, and an explicit verification flag. The registry is metadata-only at import time. Confirmation categories are configured in `config/policies.yaml`; by default, routine and moderate actions proceed while high-impact and destructive actions require approval.

Capability implementations live under `capabilities/`; discovery tools inspect local executables. Subprocesses use argument vectors and `shell=False`. The pipeline runner connects explicit `Command` stages. The rule parser is deterministic and reports unsupported/underspecified requests. `Context` keeps a bounded in-memory request/result history, the most recent operation and its observed output/error, the latest factual question and web results, and pending clarification slots. This enables short follow-ups such as «búscalo» and «eso qué» without pretending to infer information absent from context. `/history`, `history`, and `historial` display session summaries; `/forget` clears the current session. This memory is not persisted across program restarts and does not grant authorization to repeat a system-changing operation.

When deterministic parsing cannot classify a request, an available optional model may return JSON with an answer, a clarification, or up to four registered operations. The assistant builds operations with registry-defined risks, validates schemas and dependencies, then uses the regular executor and confirmation policy. Model output never runs as Python or shell code. Local Ollama is auto-detected; cloud providers require explicit configuration.
